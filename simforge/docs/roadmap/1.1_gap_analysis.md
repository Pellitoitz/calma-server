# SimForge 1.1 — Gap analysis (auditoría del repositorio)

**Rama:** `develop/simforge-1.1`, bifurcada de `v1.0.0-rc1` (`1b283a7`). Línea base de la rama: 711 tests, ruff
limpio, FREEZE `[]`, 01–05 = [59, 359, 1889.05, 477.5, 130].

Auditoría hecha sobre el código real (módulos, servicios, CLI y vistas de la UI), no sobre la documentación. El
objetivo es encontrar huecos de **producto** (descubribilidad, flujo, repetición manual, integración), no sólo de
código.

Estados: `IMPLEMENTED` · `PARTIAL` · `SCAFFOLD` · `DEFERRED` · `NOT_PRESENT`.

## 2. Flujo del ingeniero: dónde se pierde el tiempo

| Transición | Qué hace hoy el ingeniero a mano | Lo que obliga a conocer internals o editar ficheros |
|---|---|---|
| PROBLEM → MODEL | describir con NL (experimental) o escribir YAML; cargar un ejemplo y adaptarlo | añadir o conectar nodos, distribuciones, transporte, productos, setups, mantenimiento: **YAML** |
| MODEL → VERIFY → APPROVE | bien resuelto (verificación con códigos, MISSING bloquea, aprobación por hash) | — |
| RUN → ANALYZE | leer métricas por run; filtrar la traza | no hay comparación de réplicas ni rankings consolidados por recurso o nodo |
| ANALYZE → EXPERIMENT | rejilla de factores por ruta numérica (`nodes.x.params...`) | elegir la **ruta interna** del parámetro |
| EXPERIMENT / SCENARIO → COMPARE | crear el escenario (CLI) o una versión nueva; comparar físicamente **sólo vía economics** | sin clonar en la UI; sin comparación física directa |
| COMPARE → ECONOMICS | evaluar y comparar está bien; **cambiar supuestos** exige YAML | editar el bloque `economics` |
| → REPORT | informe de un run; la comparación se exporta como JSON (CLI) | no hay informe de comparación |

Cambios de interfaz forzados:

- escenarios: CLI sí, UI no;
- calendarios: UI y CLI;
- productos, mantenimiento y supuestos económicos: YAML;
- evaluar economics: UI y CLI.

Información que se pierde: el porqué de un escenario (sólo el mensaje de la versión) y la comparación física fuera de
economics.

## 3. Huecos por capa

| Capa | Huecos |
|---|---|
| Motor | **ninguno bloqueante para 1.1**. Candidato de extensión de dominio: transportador (`conveyor`) |
| Aplicación / servicios | comparación física run↔run (emparejada si hay CRN); clonar un escenario a partir del baseline; agregados de resultados (rankings factuales); informe de comparación |
| UI | constructor estructural (nodos y conexiones), editor de distribuciones y transporte, editores de productos/setups, mantenimiento y supuestos económicos, flujo de escenarios, results workbench, KPIs sobre el grafo |
| CLI | comparación física de runs; experimento sobre el proyecto (hoy `experiment` es sólo por fichero) |
| Persistencia | ninguno obligatorio: escenarios y baseline ya existen. Guardar comparaciones sería opcional (requeriría la migración 4: decisión aparte) |
| Datos | el flujo es completo. Falta enlazar mejor «parámetro del modelo ← dataset» desde la pestaña Model |
| Resultados | distribuciones por réplica, vista consolidada con IC, deltas emparejados |
| Escenarios | flujo completo baseline → clonar → modificar → ejecutar → comparar |
| Informes | comparación de escenarios; secciones de productos/setups, mantenimiento y procedencia de datos |
| Biblioteca | 19 componentes `draft` sin tests propios; sin plantillas de patrones (estación con operario, máquina + buffer, bucle de bastidores) |
| Validación | vista unificada (sólo lectura) del estado por capacidad y de los estudios |

## 4. Cuellos de botella principales

- **Flujo de ingeniería.** Construir o cambiar la **estructura** del modelo exige YAML (o el asistente IA experimental).
  Lo mismo pasa con productos, setups, mantenimiento y supuestos económicos.
- **Usabilidad.** Asimetría CLI/UI (escenarios, extensiones) y experimentos que piden rutas internas de parámetros.
- **Análisis.** No hay comparación física de dos runs o escenarios fuera de economics, ni deltas frente al baseline
  en los experimentos.
- **Informes.** El informe es de un solo run: no existe un informe de comparación de escenarios.

## 5. Lo que **no** es un hueco para 1.1

- Más física, nuevas reglas de despacho, setups, mantenimiento o fórmulas económicas.
- Optimización.
- 3D o gemelo digital.
- Validación con datos reales: es un carril paralelo y no lo resuelve el desarrollo.
