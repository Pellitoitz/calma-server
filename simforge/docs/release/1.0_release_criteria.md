# SimForge 1.0 — Release criteria (GO / NO-GO)

Comando único: `python scripts/release/check_release.py [--manifest release_manifest.json]`. Termina en **PASS** o en
**FAIL**, nunca en «probably okay». Una comprobación que no puede ejecutarse cuenta como FAIL.

## Versionado

Hay dos versiones con significados distintos. **No tienen por qué coincidir.**

| Versión | Qué representa | Fuente de verdad | Valor |
|---|---|---|---|
| **PRODUCT VERSION** | SimForge como producto o workbench: CLI, UI, persistencia, docs, empaquetado | `simforge.__version__` (en `src/simforge/__init__.py`); `pyproject.toml` la lee (`dynamic = ["version"]`, `attr = simforge.__version__`) | **`1.0.0rc1`** (forma PEP 440 de **1.0.0-rc1**) |
| **ENGINE_VERSION** | contrato y comportamiento del motor de simulación, para reproducibilidad y linaje (clave de caché física, `engine_version` de cada run, manifiesto) | `simforge.ENGINE_VERSION` | `0.9.0` |
| `ECONOMICS_ENGINE_VERSION` | identidad de las evaluaciones económicas (`evaluation_id`) | `simforge.domain.economics` | `0.9.0` |

Reglas:

- **La versión de producto** se guarda en cada run (`app_version`) y en el manifiesto (`simforge_version`). Nunca
  entra en la clave de la caché física ni en el `evaluation_id`: cambiarla no invalida resultados ni identidades.
- **ENGINE_VERSION** sólo cambia cuando cambia la semántica de simulación. Empaquetar, documentar o declarar una RC no
  la mueve: 1.0.0-rc1 se publica con el motor `0.9.0`, y su promoción a 1.0.0 tampoco obliga a cambiarlo.
- **Tags.** No se crea ningún tag (ni RC ni final) sin una instrucción explícita. La ausencia de tag tras declarar
  RC1 es intencionada.

`tests/test_release_versioning.py` comprueba:

- que hay una única fuente de verdad;
- que los metadatos instalados coinciden;
- que el motor es independiente;
- que las superficies públicas (run, manifiesto, informe, UI) son coherentes;
- que los docs de RC1 están presentes.

La instalación limpia comprueba `importlib.metadata.version("simforge") == "1.0.0rc1"`.

Después de declarar la RC: la ventana de estabilización, la política de nueva RC y los criterios de promoción a
1.0.0 están en [`1.0_stabilization_policy.md`](1.0_stabilization_policy.md). Notas de RC1:
[`1.0.0-rc1_release_notes.md`](1.0.0-rc1_release_notes.md).

## Severidad de bugs

| Sev. | Definición | Efecto en la release |
|---|---|---|
| **S0 CRITICAL** | corrupción o pérdida de datos, resultado físico erróneo, economics que modifica el DES, aprobación saltada, afirmación de validación falsa | NO-GO |
| **S1 HIGH** | run guardado no reproducible, linaje o caché erróneos, MISSING/default silencioso, migración que destruye un proyecto, instalación imposible, regresión de un ejemplo | NO-GO |
| **S2 MEDIUM** | error confuso o con traceback, documentación falsa en un caso concreto, fallo recuperable | revisión explícita, uno por uno |
| **S3 LOW** | cosmético o de comodidad | se puede diferir |

## Release blockers

Cualquiera de estos bloquea la release:

- datos corrompidos;
- run guardado no reproducible;
- resultado físico erróneo;
- MISSING o default silencioso;
- aprobación saltada;
- economics que modifica el DES;
- migración que destruye un proyecto;
- regresión de un ejemplo;
- instalación imposible;
- afirmación de validación falsa.

**No** son blockers, porque están fuera de alcance: NPV, 3D, optimización, cloud, multiusuario, IA de análisis…

## Criterios de RC (`1_0_RC_READY` sólo si se cumplen todos)

| # | Criterio | Cómo se comprueba |
|---|---|---|
| 1 | pytest completo PASS | `check_release` → `pytest_full` (sin `ANTHROPIC_API_KEY` en el entorno) |
| 2 | ruff PASS | `ruff` |
| 3 | FREEZE intacto | `freeze` |
| 4 | 01–05 exactos | `regression_01_05` = [59, 359, 1889.05, 477.5, 130] |
| 5 | workflow golden PASS | `release_suite` (`tests/test_release_golden_workflow.py`, CLI real en procesos separados) |
| 6 | instalación limpia PASS | `clean_install` (venv nuevo, paquete instalado, otro directorio, workspace vacío) |
| 7 | migraciones PASS | `release_suite` (desde vacío, desde cada versión histórica, atomicidad, copia previa) |
| 8 | reproducibilidad save/load PASS | `release_suite` (export → otro workspace → re-simular sin caché → réplicas idénticas) |
| 9 | smoke de CLI PASS | `release_suite` (`test_release_smoke.py`) |
| 10 | smoke de UI PASS | `release_suite` (AppTest, 12 pestañas, proyecto real) |
| 11 | sin S0/S1 abiertos | `1.0_gap_analysis.md` § F |
| 12 | docs básicas completas | `docs` (docs de release + 15 guías de usuario + tutorial + README de ejemplos) |
| 13 | limitaciones conocidas publicadas | `KNOWN_LIMITATIONS.md` |
| 14 | estado de validación visible | UI (cabecera), informe (§9), `docs/user/13_validation_status.md` |
| 15 | sin botones muertos | smoke de UI |
| 16 | sin afirmaciones de validación falsas | `validation_claims` + el smoke de UI comprueba que no aparece `REAL_DATA_VALIDATED` |

## Criterios de la release final 1.0.0 (además del RC)

| Criterio | Estado en esta etapa |
|---|---|
| RC estable (sin cambios de código entre el RC y la final salvo correcciones de bugs) | pendiente: requiere declarar el RC |
| ningún release blocker | sí, a fecha de esta etapa |
| tutorial de punta a punta probado | los pasos del tutorial son los del test golden |
| paquete e instalación reproducibles | `clean_install` |
| persistencia y recuperación probadas | `release_suite` |
| manifiesto de release generado | `check_release.py --manifest` |
| changelog preparado | `CHANGELOG.md` |
| identificadores de versión correctos | pendiente: `1.0.0` sólo en el momento de la release, por instrucción explícita |

La validación económica con datos reales **no** se exige para la release del software, pero su estado `NOT_EXECUTED`
es explícito en la UI, en los informes y en los docs. Un bug encontrado por una validación real puede bloquear la
release según su severidad; un `NOT_OBSERVED` no la bloquea.

## Clasificación de tests

| Marca | Contenido | Comando |
|---|---|---|
| `release` | workflow golden, persistencia, migraciones, CLI y UI smoke | `pytest -m release` |
| `validation` | protocolos de validación real (calendarios, economics) | `pytest -m validation` |
| `regression` | referencias congeladas (trazas golden, benchmark, harness LLM) | `pytest -m regression` |
| `integration` | CLI, servicios y UI de punta a punta | `pytest -m integration` |
| `unit` | todo lo demás | `pytest -m unit` |
| smoke rápido | — | `pytest -m "release and not integration" -x` o `pytest tests/test_release_smoke.py` |
| suite completa | — | `pytest` |
| suite de release | — | `python scripts/release/check_release.py` |
