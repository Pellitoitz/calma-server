# SimForge 1.0 — Stabilization policy (RC → 1.0.0)

Complementa a [`1.0_release_criteria.md`](1.0_release_criteria.md), que define las severidades S0–S3, los release
blockers y el comando `check_release.py`. Aquí se define qué ocurre **después** de declarar una RC.

## 1. Ventana de estabilización

- **Duración recomendada: 7–14 días de uso real** de la RC.
- No consiste en esperar. Durante la ventana se ejecutan **workflows reales del producto** para encontrar defectos:
  - crear proyectos, construir o importar modelos, MISSING y aprobación;
  - runs, experimentos, escenarios y evaluaciones económicas;
  - informes, manifiestos, export/import a otra máquina;
  - instalación en un entorno limpio.
- Cada sesión de uso relevante se anota en un registro de estabilización: qué workflow, qué versión y qué incidencias.
  Lo que no se ha usado no cuenta como estabilizado.
- La ventana empieza el día en que se declara la RC (commit identificado). Se reinicia si hay una nueva RC (§3).

## 2. Qué se admite durante una RC

| Admitido | No admitido |
|---|---|
| correcciones S0, S1 y S2 | features nuevas |
| S3 de bajo riesgo, claramente justificadas | capacidades DES nuevas |
| documentación incorrecta | optimización |
| problemas de instalación y empaquetado | capacidades de IA nuevas |
| problemas de persistencia | cambios de arquitectura innecesarios |
| problemas de reproducibilidad y linaje | refactors amplios |
| tests que reproducen defectos reales | cambios cosméticos con riesgo |
| | ampliación del alcance de 1.0 |

Todo bug funcional sigue exactamente esta secuencia:

**reproducción → test rojo → corrección mínima → test verde → suite completa → `check_release.py` (PASS)**

Además:

- se clasifica (S0–S3) y se anota en el registro de estabilización;
- no se ajustan resultados esperados, datos ni tolerancias para que algo pase;
- FREEZE y la regresión 01–05 deben quedar intactos;
- cualquier diferencia en 01–05 es un BLOCKER.

## 3. Cuándo hace falta una nueva RC (RC2, RC3…)

| Hallazgo después de declarar la RC | Decisión |
|---|---|
| S0 o S1 | **nueva RC** tras corregirlo; la ventana se reinicia |
| S2 que afecte a resultados, comportamiento ejecutable, persistencia, reproducibilidad, instalación, interfaces públicas o linaje | **nueva RC**; la ventana se reinicia |
| otro S2 (sin efecto en lo anterior) | decisión explícita y anotada: nueva RC o corrección dentro de la RC actual |
| corrección puramente documental | dentro de la RC actual, sin reiniciar la ventana, si todas las comprobaciones siguen verdes |
| S3 de riesgo mínimo | igual que la documental |

La decisión **no se automatiza**. Cada hallazgo deja traza en el registro y en el commit de la corrección: severidad,
efecto y decisión (nueva RC o no).

Una nueva RC es `1.0.0rcN+1`, con sus release notes, un `check_release.py` en PASS sobre su commit y un tag sólo con
autorización explícita.

## 4. Criterios de promoción a 1.0.0

La promoción es **`1.0.0-rcN → 1.0.0`**, sin aprovecharla para introducir funcionalidades. Sólo cambia la versión de
producto (`simforge.__version__ = "1.0.0"`), las release notes y el CHANGELOG. `ENGINE_VERSION` no cambia por la
promoción.

Se exigen **todos** estos criterios:

| # | Criterio |
|---|---|
| 1 | 0 S0 abiertos |
| 2 | 0 S1 abiertos |
| 3 | 0 S2 incompatibles con la release final |
| 4 | S3 restantes documentados y aceptados |
| 5 | FREEZE intacto |
| 6 | Regresión 01–05 exactamente idéntica: [59, 359, 1889.05, 477.5, 130] |
| 7 | Suite completa pasando |
| 8 | Tests de release pasando (`pytest -m release`) |
| 9 | Ruff limpio |
| 10 | Instalación limpia pasando |
| 11 | Workflow golden reproducible |
| 12 | Export/import reproducible (re-simulación sin caché, réplicas idénticas) |
| 13 | Sin defectos conocidos de linaje o reproducibilidad incompatibles con la release |
| 14 | Rendimiento dentro del criterio existente (≤ 10× la línea base guardada) |
| 15 | `KNOWN_LIMITATIONS.md` actualizado |
| 16 | Matriz de capacidades coherente |
| 17 | `CHANGELOG.md` coherente |
| 18 | Release notes coherentes |
| 19 | Uso real suficiente de la RC durante la ventana de estabilización (registro de estabilización) |
| 20 | `check_release.py` en PASS sobre el **commit exacto** candidato a la final, con el árbol limpio (`--manifest`: `working_tree_dirty: false`) |

La validación económica con datos reales **no** es requisito de la release del software. Su estado (`NOT_EXECUTED`
mientras no haya datos de planta) debe seguir siendo explícito.
